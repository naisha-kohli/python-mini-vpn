# Mini VPN Project - Network Lab and TUN-over-UDP Tunnel

## Project overview

This is a beginner-friendly Mini VPN project built and tested locally on Kali Linux.

The project uses:

- Linux network namespaces
- Virtual Ethernet (`veth`) pairs
- TUN interfaces
- UDP sockets
- Python
- `tcpdump` and Wireshark
- The `cryptography` Python library for a future encryption stage

The goal is to understand the path a VPN packet follows:

```text
Application
    ↓
Linux network stack
    ↓
TUN interface
    ↓
Python VPN program
    ↓
UDP transport network
    ↓
Python VPN program on the peer
    ↓
Peer TUN interface
    ↓
Peer Linux network stack
```

This lab runs entirely on my own Kali machine. The two network namespaces simulate two separate computers.

# Part 4 - Manual lab design

The lab contains two isolated network namespaces:

```text
vpnA = simulated computer A
vpnB = simulated computer B
```

A namespace has its own interfaces, IP addresses, routes, and network state. This lets me create two virtual machines without needing a second physical computer.

The namespaces are connected with a veth pair:

```text
vpnA                                  vpnB
vethA =============================== vethB
          virtual Ethernet cable
```

The veth pair is the underlying transport connection for the VPN's UDP packets.

# Part 5 - Network addressing

## Underlying transport network

```text
vpnA / vethA: 10.10.0.1/24
vpnB / vethB: 10.10.0.2/24
```

This network carries the outer UDP packets between VPN-A and VPN-B.

Test it with:

```bash
sudo ip netns exec vpnA ping -c 3 10.10.0.2
```

A successful ping proves that the base virtual network is working.

## Virtual VPN network

```text
vpnA / tun0: 10.20.0.1/24
vpnB / tun0: 10.20.0.2/24
```

This is the inner virtual network carried through the VPN tunnel.

# Part 8 - Python VPN peers

The project uses two Python programs:

```text
vpn.py   = VPN peer A, running inside vpnA
vpnB.py  = VPN peer B, running inside vpnB
```

Each program:

1. Opens `tun0`.
2. Reads IP packets sent by Linux to `tun0`.
3. Sends those packets through a UDP socket over `10.10.0.0/24`.
4. Receives UDP packets from the other peer.
5. Writes the original IP packets into its local `tun0`.

The Python peers must both use:

```python
b"tun0",
```

This is important because the VPN test addresses `10.20.0.1` and `10.20.0.2` are configured on `tun0`, not `tun1`.

# Part 8 - Encrypted VPN implementation

The final local VPN implementation uses:

```text
vpn_x25519.py
crypto.py
protocol.py
run-vpn.sh
```

## `run-vpn.sh`

This script rebuilds the isolated lab:

- Creates `vpnA` and `vpnB` network namespaces.
- Connects them using `vethA` and `vethB`.
- Configures the UDP transport network:

```text
vpnA: 10.10.0.1/24
vpnB: 10.10.0.2/24
```

- Configures the inner VPN network on `tun0`:

```text
vpnA: 10.20.0.1/24
vpnB: 10.20.0.2/24
```

Run it before starting the VPN peers:

```bash
cd ~/mini-vpn
sudo ./run-vpn.sh
```

## `vpn_x25519.py`

This is the final VPN peer program. The same file runs in both namespaces with different command-line options.

It performs these tasks:

1. Opens and attaches to `tun0`.
2. Opens a UDP socket on port `5555`.
3. Performs an X25519 key exchange with the peer.
4. Uses HKDF to derive a fresh AES-256-GCM session key.
5. Reads IP packets from `tun0`.
6. Encrypts packets with AES-GCM.
7. Sends encrypted packets through UDP.
8. Decrypts and authenticates packets received from the peer.
9. Writes valid decrypted packets into its local `tun0`.
10. Uses sequence numbers and a basic replay window to reject duplicate or old packets.

## `crypto.py`

This file contains the cryptographic helper functions:

- Generate an X25519 private/public key pair.
- Derive a shared secret from the local private key and peer public key.
- Derive a 32-byte AES session key using HKDF-SHA256.
- Encrypt packets with AES-256-GCM.
- Decrypt and authenticate received packets.

## `protocol.py`

This file defines the Mini VPN packet format.

Each data packet contains:

```text
+---------+---------+-----------------+----------------+------------------+
| Version | Type    | Sequence Number | 12-byte Nonce  | Ciphertext + Tag |
+---------+---------+-----------------+----------------+------------------+
```

- **Version** identifies the protocol format.
- **Type** identifies a handshake or encrypted-data packet.
- **Sequence number** helps identify old or duplicate packets.
- **Nonce** is a unique encryption value.
- **Ciphertext + tag** contains the encrypted IP packet and its authentication data.

# Part 9 - Start the encrypted Mini VPN

Open two terminals.

## Terminal 1 - VPN-A

```bash
cd ~/mini-vpn
sudo ip netns exec vpnA "$HOME/mini-vpn/.venv/bin/python" "$HOME/mini-vpn/vpn_x25519.py" --tun tun0 --listen-ip 10.10.0.1 --peer-ip 10.10.0.2 --port 5555 --name VPN-A
```

## Terminal 2 - VPN-B

```bash
cd ~/mini-vpn
sudo ip netns exec vpnB "$HOME/mini-vpn/.venv/bin/python" "$HOME/mini-vpn/vpn_x25519.py" --tun tun0 --listen-ip 10.10.0.2 --peer-ip 10.10.0.1 --port 5555 --name VPN-B
```

Expected result in both terminals:

```text
X25519 handshake complete; AES-GCM session key ready
```

This confirms that both peers created the same fresh session key without storing a hardcoded encryption key.

# Part 11 - Verify encrypted traffic

Capture the outer UDP transport traffic:

```bash
sudo ip netns exec vpnA tcpdump -ni vethA udp port 5555 -X
```

Then generate tunnel traffic again:

```bash
sudo ip netns exec vpnA ping -c 3 10.20.0.2
```

The UDP payload appears as unreadable ciphertext. This is expected because the original ICMP packet is encrypted before crossing the transport network.

To view the readable inner traffic before encryption, capture `tun0`:

```bash
sudo ip netns exec vpnA tcpdump -ni tun0 icmp
```

This demonstrates the difference between:

```text
tun0  = readable inner VPN traffic
vethA = encrypted outer UDP traffic
```

The Mini VPN project successfully implements a local encrypted point-to-point VPN lab.

Completed features:

- Linux network namespaces
- veth transport network
- TUN interfaces
- TUN-over-UDP packet forwarding
- AES-256-GCM encryption and authentication

- Packet versioning and sequence numbers

- Packet capture and verification with `tcpdump`

## Limitations

This project is an educational local lab, not a production VPN.

It does not include:

- Full-tunnel Internet routing
- NAT or gateway mode
- Peer identity authentication
- Rekeying
- MTU handling
- Robust connection timeout and recovery logic
- Production security auditing

The project should remain in an isolated lab environment and should not be exposed to the public Internet.
